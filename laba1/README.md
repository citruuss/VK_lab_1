## 2\. Поднятые сервисы — и почему именно они

Перечисли, что реально поднял (проверь через `docker ps`), и обоснуй выбор каждой технологии.

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
| :---- | :---- | :---- |
| MinIO | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы) | Выбрала, потому что работает также, как и AWS S3, но локально и бесплатно. |
| PostgreSQL | БД, где Lakekeeper хранит метаданные каталога | Надёжная база, которую все знают и Lakekeeper умеет с ней работать  |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | Говорит Trino, где лежат файлы. Без него MinIO просто куча файлов и непонятно, что к чему относится. |
| Trino | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | Читает данные из MinIO через Lakekeeper. Умеет делать JOIN поверх файлов. Еще есть Spark, но он тяжелее и для интерактивных запросов не так удобен. |
| (BI: Superset / Metabase) | отчёт/дашборд поверх Gold | Отчёт/дашборд поверх Gold. Выбрала Metabase, потому что он легковесный, запускается одной командой в Docker и имеет понятный UI для быстрого просмотра данных без написания кода. |

### Скрипты, которыми поднимал стек

**Сначала создала папку и конфиг для Trino:**

mkdir lakehouse-pr1  
cd lakehouse-pr1  
mkdir trino-catalog

**Потом создала файл trino-calatog/iceberg.properties:**

connector.name=iceberg  
iceberg.catalog.type=rest  
iceberg.rest-catalog.uri=http\://lakekeeper:8181  
iceberg.rest-catalog.warehouse=s3://lakehouse  
hive.s3.path-style-access=true  
hive.s3.endpoint=http\://minio:9000  
hive.s3.aws-access-key=admin  
hive.s3.aws-secret-key=password123

**Запустила MinIO — хранилище:**

docker run \-d \--name minio \--network lakehouse-net \\  
  \-e MINIO\_ROOT\_USER=admin \\  
  \-e MINIO\_ROOT\_PASSWORD=password123 \\  
  \-p 9000:9000 \-p 9001:9001 \\  
  minio/minio server /data \--console-address ":9001"

**Запустила PostgreSQL — база для метаданных:**

docker run \-d \--name postgres \--network lakehouse-net \\  
  \-e POSTGRES\_USER=lakekeeper \\  
  \-e POSTGRES\_PASSWORD=lakekeeper \\  
  \-e POSTGRES\_DB=lakekeeper \\  
  \-p 5432:5432 \\  
  postgres:15

**Запустила Lakekeeper — каталог:**

docker run \-d \--name lakekeeper \--network lakehouse-net \\  
  \-e LAKEKEEPER\_\_STORAGE\_\_TYPE=s3 \\  
  \-e LAKEKEEPER\_\_STORAGE\_\_S3\_\_ENDPOINT=http\://minio:9000 \\  
  \-e LAKEKEEPER\_\_STORAGE\_\_S3\_\_ACCESS\_KEY=admin \\  
  \-e LAKEKEEPER\_\_STORAGE\_\_S3\_\_SECRET\_KEY=password123 \\  
  \-e LAKEKEEPER\_\_STORAGE\_\_S3\_\_BUCKET=lakehouse \\  
  \-e LAKEKEEPER\_\_STORAGE\_\_S3\_\_REGION=us-east-1 \\  
  \-e LAKEKEEPER\_\_DATABASE\_\_URL=postgresql://lakekeeper:lakekeeper@postgres:5432/lakekeeper \\  
  \-p 8181:8181 \\  
  ghcr.io/lakekeeper/lakekeeper:latest

**Запустила Trino:**

docker run \-d \--name trino \--network lakehouse-net \\  
  \-v ./trino-catalog:/etc/trino/catalog \\  
  \-p 8080:8080 \\  
  trinodb/trino:430

**Запустила Metabase, BI-инструмент для визуализации:**  
docker run \-d \--name metabase \--network lakehouse-net \\  
\-p 3000:3000 \\  
metabase/metabase:latest

## 3\. Разбор запроса — какие данные нужны

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
| :---- | :---- | :---- |
| part | partkey, brand, type, size | Фильтрую по бренду, типу и размеру. Группирую по этим колонкам. |
| partsupp | partkey, suppkey | JOIN с part по partkey. Считаю уникальных поставщиков. |
| supplier | suppkey, comment | Подзапрос: ищу поставщиков с жалобами в комментариях, потом исключаю их. |

## 6\. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
| :---- | :---- |
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Обычные БД типа PostgreSQL не справляются с петабайтами данных, они слишком дорогие и не масштабируются. Data Lake дешёвый, но там нет транзакций: можно случайно испортить данные. Lakehouse берёт лучшее от обоих: дешёвое хранение как в озере, но с надёжностью как в хранилище. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | Если добавить колонку через ALTER TABLE \- ADD COLUMN, старые файлы не меняются. Trino просто подставит NULL для старых строк, где этой колонки не было. Новые данные будут писаться с новой колонкой. Это удобно и  не нужно переписывать всё заново. |
| Пример скрипта восстановления данных из снапшота (time travel) | SELECT \* FROM iceberg.lakehouse.silver\_parts\_filtered FOR TIMESTAMP AS OF (CURRENT\_TIMESTAMP \- INTERVAL ‘1’ DAY). Этот запрос вернёт данные такими, какими они были вчера. Iceberg хранит все версии данных, поэтому можно откатиться, если сегодня загрузили что-то не то. |

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
| :---- | :---- |
| Metabase (BI) | Выбрала Metabase вместо Superset, потому что он легковесный. Запускается одной командой в Docker, не требует сложной инициализации и создания администратора через консоль. У него понятный UI, и он отлично подходит для быстрого просмотра данных. |

**Действия в UI:**

Зашла в веб\-интерфейс Metabase по адресу http\://localhost:3000

При первом входе создала аккаунт.

Перешла в настройки \-\> Databases \-\> Add database.

Выбрала тип базы данных Trino.		

Заполнила параметры подключения: Host, trino,  Port 8080, Catalog, iceberg, Schema, lakehouse.

Нажала Save — подключение прошло успешно.

Открыла встроенный SQL-редактор и выполнила запрос к Bronze-слою:

   SELECT \* FROM iceberg.lakehouse.bronze\_part LIMIT 10;

Увидела таблицу с данными деталей (partkey, brand, type, size) — это подтверждает, что BI-инструмент успешно читает сырые данные из Lakehouse.

## 7\. Выводы

Развернула Lakehouse из MinIO, PostgreSQL, Lakekeeper и Trino. Сделала медальон из трёх слоёв: сырые данные в Bronze, очищенные в Silver, готовая витрина в Gold. Это удобно и если что-то сломается в очистке, можно начать заново из Bronze, не обращаясь к источнику. Parquet со сжатием ZSTD работает быстрее, чем GZIP, хоть и занимает чуть больше места. Для аналитики скорость важнее, поэтому ZSTD самый нормальный выбор. Lakehouse даёт гибкость: можно хранить данные дёшево в S3, но при этом иметь надёжность и возможность делать сложные запросы через Trino.
